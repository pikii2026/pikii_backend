# 제출 문서 작성 자료

창의적 SW경진대회 SW프로그램 개발 부문 제출용. **SW명세서**와 **프로젝트 결과보고서**에 들어갈 내용을 각각 정리했다.

## 두 문서의 차이

|          | SW명세서            | 프로젝트 결과보고서         |
|:-------- |:---------------- |:------------------ |
| 답하는 질문   | 무엇을, 어떻게 만들었는가   | 왜 만들었고, 무엇을 이뤘는가   |
| 성격       | 기술 문서 (구조·설계)    | 서사 문서 (배경→과정→성과)   |
| 독자       | 기술 심사위원          | 전체 심사위원 (비전공 포함)   |
| 기능 서술 방식 | 동작 방식 (입력·처리·출력) | 사용자 가치 (무엇을 해결하는가) |

# PART 1. SW명세서

## 1. 개요

### 1.1 소프트웨어 정보

| 항목     | 내용                               |
|:------ |:-------------------------------- |
| 소프트웨어명 | Pickii (피키)                      |
| 분류     | 모바일 애플리케이션 + REST API 서버         |
| 정의     | 대학생 팀 프로젝트·공모전 팀원 매칭 및 협업 관리 플랫폼 |
| 대상 사용자 | 팀 단위 활동(공모전·프로젝트·스터디)을 준비하는 대학생  |

### 1.2 개발 범위

| 구분  | 범위                                                                           |
|:--- |:---------------------------------------------------------------------------- |
| 포함  | 회원·인증, 이력서(프로필), 공고·지원, 프로젝트 관리, 실시간 채팅, 일정 관리, 회의 시간 조율, 상호평가, AI 보조 기능, 알림 |
| 제외  | 결제, 관리자 웹 콘솔, 다국어 지원                                                         |

### 1.3 용어 정의

| 용어                  | 설명                                                |
|:------------------- |:------------------------------------------------- |
| 공고(Recruit)         | 팀원을 모집하기 위해 작성하는 게시물                              |
| 지원(Apply)           | 공고에 참여 의사를 밝히는 행위 및 그 지원서                         |
| 프로젝트(Project)       | 공고 작성자가 그룹 채팅을 생성한 시점에 전환되는 팀 단위                  |
| 회의 조율(Meeting Poll) | 팀원 가능 시간을 수집해 회의 일정을 확정하는 절차                      |
| 교내 공고(onCampus)     | 작성자와 동일 대학 소속 회원에게만 노출되는 공고                       |
| 상호평가(Feedback)      | 프로젝트 종료 후 팀원 간 익명 평가                              |
| RTR                 | Refresh Token Rotation. 갱신 시 리프레시 토큰을 재발급하는 보안 기법 |

## 4. 소프트웨어 아키텍처

### 4.1 계층 구조

```
Controller  →  Service  →  Repository  →  DB
 요청/응답     비즈니스 로직    데이터 접근
              트랜잭션 경계
```

| 계층         | 책임                                      | 금지 사항                         |
|:---------- |:--------------------------------------- |:----------------------------- |
| Controller | 요청 DTO 수신, 입력 검증(`@Valid`), 공통 응답 형식 변환 | 비즈니스 로직, Repository 직접 호출     |
| Service    | 비즈니스 로직, 트랜잭션 관리, 예외 발생                 | 웹 계층 의존(HttpServletRequest 등) |
| Repository | 쿼리 메서드 정의                               | 비즈니스 판단                       |
| DTO        | 요청/응답 데이터 전달 (Java `record`)            | 엔티티 직접 노출                     |

### 4.2 패키지 구조

```
com.pickii
├── global                    # 전 도메인 공통
│   ├── common/response       # ApiResponse, PageResponse
│   ├── exception             # ErrorCode, BusinessException, 전역 예외 처리
│   ├── security              # SecurityConfig, JWT 발급·검증·필터
│   ├── mail                  # MailClient 추상화 (SMTP / Brevo API)
│   ├── fcm                   # Firebase 초기화, 푸시 발송
│   ├── ai                    # Gemini 클라이언트
│   └── config                # Swagger, JPA Auditing
└── domain                    # 도메인별 entity/repository/service/controller/dto
    ├── auth                  # 인증 정책, Redis Key
    ├── member                # 회원, 소셜 연동, 대학교
    ├── resume                # 이력서, 기술스택, 자격증, 링크
    ├── recruit               # 공고, 카테고리·주제, 댓글, 스크랩
    ├── apply                 # 지원서, 지원 키워드
    ├── project               # 프로젝트, 팀원
    ├── schedule              # 개인·팀 일정, 회의 조율
    ├── chat                  # 채팅방(MySQL) + 메시지(MongoDB)
    ├── notification          # 알림 설정, 알림 내역, 디바이스 토큰
    └── feedback              # 상호평가, AI 피드백
```

### 4.3 공통 설계 규칙

- **응답 형식 통일**: 성공은 `{ data, timestamp }`, 실패는 `{ error: { code, message }, timestamp }`

- **예외 처리 일원화**: `BusinessException(ErrorCode)` → 전역 핸들러가 HTTP 상태·에러 코드로 변환

- **Null 정책**: 값이 없는 필드는 응답에서 제외 (`NON_NULL`)

- **시간 형식**: 전 API가 ISO-8601 / KST(UTC+9)

- **엔티티 불변성**: Setter 금지, 상태 변경은 의미 있는 메서드로 (`recruit.close()`, `apply.accept()`)

## 5. 데이터베이스 설계

### 5.1 설계 원칙

1. **ENUM 지양** — 상태값은 `VARCHAR`로 저장하고 애플리케이션 Enum으로 제어 (DDL 변경 부담 최소화)
2. **삭제 정책 이원화**
   - 일반 데이터(공고·댓글): `DeletedAt`을 이용한 Soft Delete
   - 회원 정보: 개인정보 보호를 위해 Hard Delete, 작성 이력은 FK를 `NULL` 처리해 '알 수 없음'으로 보존
3. **감사 컬럼** — `CreatedAt`, `UpdatedAt` 기본 포함
4. **비밀번호** — BCrypt 단방향 암호화

### 5.2 도메인별 주요 테이블 (MySQL)

### 5.6 ERD

전체 ERD는 **`docs/ERD.svg`** 참조 (2254 × 1138). 엔티티 소스 코드에서 테이블·컬럼·관계를 추출해 생성했다.

- 테이블 44개(MySQL) + 컬렉션 1개(MongoDB), 관계 60개
- **관계 중심 배치** — 참조 관계가 있는 테이블끼리 가깝게 놓이도록 배치를 최적화했다. `Member`(관계 26개)가 중앙 허브이며, `Project`(8개)·`Recruit`(7개)가 각 영역의 중심을 이룬다
- 색상은 도메인 구분용 (회원·이력서·공고·지원·프로젝트·일정·채팅·알림·상호평가)
- 실선 = 객체 참조(FK), 점선 = 식별자 참조(Long FK), 화살표는 참조 방향
- 각 테이블은 주요 컬럼만 표시(최대 7개), PK/FK 표기

### 6.2 주요 기능 상세 (입력–처리–출력)

#### 회원가입

| 구분  | 내용                                                                                                 |
|:--- |:-------------------------------------------------------------------------------------------------- |
| 입력  | 이메일, 비밀번호, 닉네임, 약관 동의, 이메일 인증 토큰                                                                   |
| 처리  | ① 인증 토큰 유효성 검증 ② 이메일·닉네임 중복 검사 ③ 비밀번호 정책 검증(8~20자, 대소문자·숫자 포함) ④ BCrypt 암호화 ⑤ 회원 저장 ⑥ 알림 설정 기본값 생성 |
| 출력  | 회원 ID, 가입 완료 응답                                                                                    |
| 예외  | `EMAIL_ALREADY_EXISTS`, `NICKNAME_ALREADY_EXISTS`, `INVALID_VERIFICATION_TOKEN`                    |

#### 이메일 인증

| 구분   | 내용                                                                                         |
|:---- |:------------------------------------------------------------------------------------------ |
| 입력   | 이메일, 인증 목적(가입/비밀번호 재설정)                                                                    |
| 처리   | ① 목적별 가입 여부 검증 ② 재발송 쿨다운 확인 ③ IP 기준 요청 제한(10분 5회) ④ 6자리 코드 생성 ⑤ 메일 발송 ⑥ Redis 저장(TTL 180초) |
| 출력   | 발송 완료 응답                                                                                   |
| 특이사항 | 발송 성공 후에만 Redis에 저장해, 실패 시 재요청이 막히지 않도록 설계                                                 |

#### 공고 검색

| 구분  | 내용                                                                       |
|:--- |:------------------------------------------------------------------------ |
| 입력  | 검색어(2~30자), 교내/교외, 카테고리 ID 목록, 주제 ID 목록, 페이지                             |
| 처리  | ① 조건 간 AND, 같은 그룹 내 OR로 필터 구성 ② 교내 공고는 조회자와 `univId`가 같은 경우만 포함 ③ 페이징 조회 |
| 출력  | 공고 목록(제목·작성자·모집 상태·인원 현황), 전체 건수                                         |

| 구분    | 내용                                                                                                         |
|:----- |:---------------------------------------------------------------------------------------------------------- |
| 입력    | 회의명, 소요 시간(30/60/90/120분), 탐색 기간, 탐색 시간대, 응답 마감 시간, 참가 팀원                                                  |

## 9. 보안 설계

### 9.1 인증·인가

| 항목            | 설계                                                    |
|:------------- |:----------------------------------------------------- |
| 인증 방식         | JWT 기반 Stateless 인증                                   |
| Access Token  | 유효기간 30분                                              |
| Refresh Token | 자동 로그인 미사용 1일 / 사용 시 30일, Redis 저장                    |
| RTR           | 토큰 갱신 시 Refresh Token을 재발급하고 기존 토큰 폐기                 |
| 로그아웃          | Refresh Token 삭제 + Access Token 블랙리스트 등록              |
| 기기 관리         | 기기 식별자(deviceId)별 Refresh Token 관리, 동일 기기 재로그인 시 덮어쓰기 |

### 9.2 데이터 보호

| 항목       | 설계                                   |
|:-------- |:------------------------------------ |
| 비밀번호     | BCrypt 단방향 해시, 평문 저장·전송 없음           |
| 비밀번호 정책  | 8~20자, 영문 대문자·소문자·숫자 각 1자 이상         |
| 회원 탈퇴    | 개인정보 물리 삭제, 작성 이력은 익명화 보존            |
| 비밀번호 변경  | 전 기기 Refresh Token 삭제로 강제 로그아웃       |
| 민감 정보 관리 | API 키·DB 접속 정보는 전부 환경변수로 분리, 소스에 미포함 |

### 9.3 공격 대응

| 위협            | 대응                                  |
|:------------- |:----------------------------------- |
| 무차별 인증 코드 요청  | 재발송 쿨다운 + IP 기준 요청 제한(10분 5회)       |
| 소셜 토큰 위조      | 클라이언트 전달 토큰을 서버가 카카오 API로 재검증 후 폐기  |
| 권한 없는 자원 접근   | Service 계층에서 프로젝트 멤버·리더 여부를 매 요청 검증 |
| SQL Injection | JPA 파라미터 바인딩 사용                     |
| 토큰 탈취         | RTR + 짧은 Access Token 수명            |

# PART 2. 프로젝트 결과보고서

## 1. 개발 배경 및 필요성

*(팀 논의로 구체화 필요 — 아래는 방향 제안)*

- 대학생의 공모전·프로젝트 참여는 늘고 있으나, 팀원을 구하는 수단은 오픈채팅·에브리타임 등에 분산되어 있다
- 기존 수단의 한계
  - 상대의 역량·성실도를 판단할 근거가 없음 (프로필 부재)
  - 모집 글이 실시간 스트림에 묻혀 탐색·필터링 불가
  - 팀 결성 이후 협업 도구가 완전히 분리되어 일정 조율이 카카오톡 대화로 처리됨
- 결과적으로 팀 결성 실패, 중도 이탈, 무임승차 문제가 반복

> 설문·인터뷰 등 근거 자료삽입

## 2. 개발 목표

1. 이력서 기반으로 팀원의 역량을 사전에 확인할 수 있는 매칭 구조 제공
2. 모집–협업–평가로 이어지는 전 과정을 하나의 서비스에서 처리
3. AI를 활용해 글쓰기 부담(공고·지원서·자기소개)을 낮춤
4. 상호평가를 누적해 신뢰 기반 매칭 환경 조성

## 3. 기존 서비스 분석 및 차별성

## 6. 기술적 이슈와 해결

발표에서 가장 차별화되는 부분. 실제로 겪고 해결한 사례를 기록한다.

| 문제                     | 원인                                                  | 해결                                                                                |
|:---------------------- |:--------------------------------------------------- |:--------------------------------------------------------------------------------- |
| 배포 환경에서 인증 메일이 발송되지 않음 | 클라우드 호스팅이 스팸 방지를 위해 SMTP 포트(25·465·587·2525)를 전면 차단 | 메일 발송을 `MailClient` 인터페이스로 추상화하고 로컬은 SMTP, 운영은 HTTPS API(Brevo)를 쓰도록 구현체를 프로필로 분리 |
| 서버 컨테이너가 반복 재시작        | 저사양 환경에 맞춘 과도한 JVM 메모리 제한으로 Metaspace 고갈            | 힙을 컨테이너 메모리 비례로 전환하고 메타스페이스 상한 재조정                                                |
| 배포 직후 서버 기동 실패         | MongoDB 접속 URI에 데이터베이스명이 누락                         | 환경변수 조립 규칙 정비, 프로필별 설정 분리                                                         |
| 반복 일정을 DB 질의로 조회 불가    | RRULE(RFC 5545)은 SQL로 전개할 수 없음                      | 조회 범위 내에서 애플리케이션이 일정을 전개하는 구조로 설계                                                 |
| 푸시 키 미설정 환경에서 서버 다운 위험 | Firebase 초기화 실패가 애플리케이션 부팅 실패로 전파                   | 키가 없으면 푸시 기능만 비활성화하고 서버는 정상 기동하도록 격리                                              |
| 자격증 마스터 데이터 관리 한계      | 국가·민간 자격증이 수만 종이라 목록을 고정할 수 없음                      | 마스터에 없는 값은 사용자 입력을 그대로 등록하는 방식으로 전환                                               |
