## 결합 지점 재확인 (인원1 Day11과 동일한 지점, B트랙 관점)

### 인원1이 여러분의 코드를 호출하는 곳
- `ApplyService.updateStatus()`(4-8)에서 `ProjectRepository.findByRecruitId()`, `ChatRoomRepository.findByProjectId()`를 호출해 지원 수락 시 기존 프로젝트에 자동 합류시킵니다. **이 메서드들의 시그니처를 오늘 바꾸지 마세요.** 바꿔야 한다면 인원1에게 먼저 알리세요.
- `FeedbackService`(4-9~4-12)에서 `Project.isEnded()`, `Project.getUpdatedAt()` 등을 그대로 사용합니다. `Project` 엔티티 필드명을 바꾸면 인원1 쪽 컴파일이 깨질 수 있습니다.

### 여러분이 인원1의 코드를 호출해야 하는 곳 (오늘 점검 대상)
- Project 종료(6-4)/연장(6-5) 시 `NotificationSender.send(...)` 호출이 실제로 붙어있는지 (지금까지 TODO로 남겨뒀다면 오늘 연결)
- 회의 조율 개설(7-10)/확정(7-13) 시 알림 발송 연결
- 팀원 퇴출/나가기(6-6, 6-7) 시 `Recruit.decreaseCurrentCount()`가 실제로 호출되고 있는지 (Day2에 만들어뒀던 것)

## 점검 체크리스트

- [ ] 인원1이 만든 3-11(지원하기)로 실제 지원 → 4-8로 수락 → **이미 있는 프로젝트에 자동 합류되는지** 실제 API 호출로 확인 (지금까지는 SQL로 데이터를 직접 심어서 테스트했다면, 오늘은 진짜 API 체인으로 확인)
- [ ] 프로젝트 생성(6-1) → 그룹 채팅방 생성 확인 → 채팅 메시지 송수신(WebSocket) 정상 동작
- [ ] 회의 조율 전체 흐름(개설→응답→확정) → 팀 캘린더 반영 확인
- [ ] 프로젝트 종료(6-4) → 인원1의 상호평가(4-10) API로 평가 작성 가능한지
- [ ] 알림(NotificationHistory)에 여러분 도메인에서 발생한 이벤트(프로젝트 종료확인, 회의 조율 마감임박, 새 메시지 등)가 실제로 쌓이는지
- [ ] `Recruit.currentCount`가 지원 수락(+1)과 팀원 이탈/퇴출(-1)에서 정확히 오르내리는지 (양쪽 다 확인 — 이 필드는 인원1/인원2가 각각 다른 시점에 건드린 필드라 어긋나기 쉽습니다)
